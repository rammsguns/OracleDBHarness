## Findings and assignments

### C23 — P1: repaired proposals still depend on the original Markdown state

In `services/api/harness_api/copilot/service.py:670`, `_keep_edit_contract()`
appends the rendered repair to the original answer. `_capture_proposal()` then
parses that combined Markdown, rather than using the accepted repair blocks.
An unclosed original fence changes what that second parse captures.

Independent service reproductions used `fix01_payload()` and the existing
scripted `Replies` provider from `test_k7_edit_contract.py`. For each of these
first replies, return the test's complete `FIXED` function in a closed `plsql`
fence as the second reply:

| First reply | Actual result |
| --- | --- |
| `Here is the explanation:\n` followed by an unclosed `text` fence and `An incomplete draft` | `edit_contract` reports `proposal/repaired`, but no proposal event exists |
| Same draft with an unclosed `plsql` fence | `proposal/repaired`, but proposedText includes `An incomplete draft`, the new opening fence, and the repaired function |

Both assertions that the proposal equals `FIXED` fail. This directly contradicts
the claim that the accepted repair and applied text are the same. Structural
warnings still exist, but they do not make the corrupted replacement correct.

**Assignment:** carry accepted code blocks and document/part identity through
proposal creation as data. Render the answer safely without allowing malformed
earlier Markdown to change the proposal. Keep original replies reviewable and
preserve staleness, authorization, complete-unit warnings and multi-part atomicity.
Add service controls for unclosed text/SQL/backtick/tilde fences, quoted source,
part labels and malformed repairs. Verify both visible rendering and exact
proposedText. Do not solve this by extracting arbitrary prose as SQL.

### C24 — P1: Q3 does not yet validate evidence scope or claim meaning

`claim_checks.py:469` groups all successful evidence by operation ID. It does not
bind a proposed next check to the target, filters or page that were actually read.
Its phrase matching also ignores negation. `claim_checks.py:556` checks an offered
historical claim before applying hedging checks and does not identify which
evidence source the proposed check would consult.

Independent pure-function reproductions used one successful lookup:

```python
LookupFacts(
    "dba.scheduler_run_history",
    True,
    ["STATUS"],
    [["SUCCEEDED"]],
    {"owner": "APP", "job_name": "NIGHTLY", "row_limit": 20},
    sequence=1,
)
```

`review_claims()` incorrectly flags all of the following:

- `Increase row_limit for dba.scheduler_run_history(owner=APP, job_name=WEEKLY) to inspect its run history.`
  Evidence about NIGHTLY does not establish WEEKLY's coverage. The proposed
  parameters already identify a different question.
- `Do not increase row_limit for dba.scheduler_run_history: the result is complete.`
  This is the correct recommendation, not a request for more rows.
- `A current catalog query cannot show whether the synonym was dropped.`
  This correctly states the limitation the checker itself is enforcing.
- `Ask the DBA to check the retained DDL audit trail to determine whether the synonym was dropped.`
  This proposes a separate historical source, not a current-catalog lookup. Whether
  suitable audit evidence exists remains a prerequisite; the harness must not claim
  it has read that evidence or forbid a conditional manual investigation.

There is also a concrete evidence-identity gap in the existing change-location
check, which Q3 relies on. With only APP.PKG source read:

```python
source = LookupFacts(
    "schema.object_source",
    True,
    ["OWNER", "NAME", "TYPE", "LINE", "TEXT"],
    [["APP", "PKG", "PACKAGE BODY", 1, "PACKAGE BODY PKG AS"]],
    {"owner": "APP", "object_name": "PKG", "object_type": "PACKAGE BODY"},
    sequence=1,
)
review_claims("The fix belongs in OTHER.PKG.", [source]).findings
# Actual: []
```

At `claim_checks.py:404`, any matching identifier component or occurrence in
returned source text counts as support. A matching package name in another schema
does not mean its source was read; mentioning a dependency is not reading it.
This gap predates Q3, but it prevents the current Q3 acceptance criterion from closing.

The new lookup record is useful provenance. It does not implement the planned
answer contract for facts, inferences, unknowns, next checks and suggested changes,
nor validate those references against matching object/source scope. Appending a
coverage record and adding more phrase patterns is not completion of that package.

**Assignment:** bind diagnosis claims and proposed checks to explicit lookup/source
references and canonical target/type/filter/page scope, then validate that scope
locally. Distinguish positive assertions from negation and conditional/manual
checks. Preserve unknowns when the supported contract cannot resolve a statement;
never issue a confident correction based on another target's evidence. Render
supported factual fields from evidence where feasible, as Q3 requires. Cover both
false positives above and the wrong-owner false negative, mixed complete/truncated
results for different targets, partial source ranges and denied evidence. Retain
the actual bad-answer controls. The reproductions here become implementation inputs;
use fresh independent variations at the next checkpoint.

### C25 — P2: failed edit repairs are persisted as successful requests

`_keep_edit_contract()` returns after emitting `missing/failed:*`; it does not
propagate failure to the request's terminal outcome. At `service.py:555` and
the finalization path, the original `succeeded` outcome remains.

A service reproduction with the existing trial-18 unfenced answer followed by
`Still no proposal.` emits:

```text
edit_contract: delivered=missing, repair=failed:missing
proposal: absent
done: outcome=succeeded
```

The new timeout test explicitly expects this same success on `failed:wall_time`.
The drawer does show a missing-proposal notice and proposalPresent still fails a
case that requires code; neither corrects the persisted outcome or legacy clients
that ignore the new event. This is the explicit-failed-answer requirement in Q2.

**Assignment:** propagate missing required output to a defined non-success terminal
outcome and persisted request record, including repair timeout/provider failure.
Preserve accumulated usage and the original answer for review. Test SSE, persisted
outcome and evaluator behavior; genuine `No code change:` diagnoses remain distinct.
Do not relax the case's required-proposal or expected-outcome checks.

### C26 — P2: published protocol changes are lost on regeneration

Calling `packages/contracts/generate.py`'s `copilot_protocol_schema()` in memory
and comparing it with the published JSON shows four events would disappear:
`claim_check`, `revision`, `edit_contract`, `lookup_record`. No files were regenerated
in this review. The current contract test checks the edited artifact's event names
but does not compare it with generator output. Claude disclosed the drift, but it
is still an unfinished protocol change, not a reason to leave regeneration broken.

**Assignment:** update the generator's source of truth, regenerate the published
contract and test parity with generated output, including the new required fields.
Verify TypeScript/protocol compatibility after regeneration. Keep the same candidate
protocol version unless another compatibility change actually requires a bump.
