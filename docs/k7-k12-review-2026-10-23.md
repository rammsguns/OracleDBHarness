## 1. Commit and Implementation Analysis

Commit `9e44a53` (*fix(copilot): lock-wait semantics, scheduler counters, requester access (K12)*)
addresses three distinct failure modes identified across Q5 pooled attempts:

### 1.1 Oracle 19c Accuracy Assessment
The prompt updates in `context.py` and the finding message in `claim_checks.py` were verified
against Oracle Database 19c core documentation:

- **Enqueue & Row-Lock Waits**: In Oracle 19c, an enqueue request (e.g., TX row lock in exclusive
  mode) enqueues and blocks indefinitely until the holding transaction commits or rolls back, or
  until deadlocked/killed. It raises no exception or error.
  *Verdict: Accurate.*
- **ORA-00054**: Signaled for `NOWAIT` DML/DDL or when `DDL_LOCK_TIMEOUT` expires while waiting
  for exclusive table/object metadata enqueues.
  *Verdict: Accurate.*
- **ORA-30006**: Specifically raised by `SELECT ... FOR UPDATE WAIT n` when the timeout `n` expires.
  *Verdict: Accurate.*
- **ORA-00060**: Deadlock detection victim selection rolls back **only the statement** that detected
  the deadlock, leaving the remainder of the session's transaction intact.
  *Verdict: Accurate.*
- **Scheduler Counters**: In `DBA_SCHEDULER_JOBS`, `RUN_COUNT` and `FAILURE_COUNT` are cumulative
  lifetime counters since job creation. `DBA_SCHEDULER_JOB_RUN_DETAILS` and `DBA_SCHEDULER_JOB_LOG`
  are purged based on `LOG_HISTORY` (default 30 days). Counters larger than retained log entries
  are standard behavior.
  *Verdict: Accurate.*

The prose added to `context.py` is concise (+3 lines in Scheduler, +5 lines in Swallowed exceptions),
addresses the specific misconceptions observed in Q5 runs, and avoids overstatement.

### 2.3 Deep Analysis of False Positives
The two false positive mechanisms are:
1. **Unscoped `bare blocking` and `row[- ]locks?`**:
   The regex pattern `_LOCK_WAIT` matches `blocking(?!\s+(?:delet|insert|updat)\w*)` and `row[- ]locks?`.
   When an answer explains that a blocking session or row lock holder is involved while an error
   was raised elsewhere in the same sentence (e.g. `LEG-02`: `"the blocking session holds row locks while the error is raised elsewhere"`),
   the sentence is treated as a single clause because `while` without a comma does not trigger a turn
   in `subclauses()`. The presence of `error` and `raised` in the same clause satisfies both
   `_EXCEPTION_CONTEXT` and `_EXCEPTION_ACTION`, triggering an unjustified flag.
2. **Missing Prepositional Denials (`without raising/throwing`)**:
   In `LEG-18` (`"Blocking sessions can be monitored in v$session without throwing any database errors"`),
   `_WAIT_DENIAL` failed to match because it expects `(does|do|can|will|would) not rais\w*` or `no error/exception`.
   Prepositional phrases using `without (raising|throwing|causing)` are standard English for denying
   that an event raises an error, but are completely absent from `_WAIT_DENIAL`.

## 3. Fallback and Settlement Risk in `service.py`

In `services/api/harness_api/copilot/service.py`, `lock_wait_exception` is integrated across both
plain answers (`_plain_review`) and Kiwi diagnoses (`_kiwi_review` via `review_claims`):

1. **Revision Triggering**:
   Any `lock_wait_exception` finding triggers an immediate revision turn (`action: revise`),
   consuming request wall-time budget. If provider latency is high, this risks `skipped:wall_time`.
2. **Settlement in Plain Answers (`_settle_plain`)**:
   If a revised explanation retains the flagged phrasing, `_settle_plain` removes the offending
   sentence using `_without_statement`. In narrow explanation rubrics (such as EXPLAIN-06), if a
   legitimate sentence discussing row lock contention or blocking is stripped, the answer may fail
   the rubric's completeness or correctness criteria.
3. **Catastrophic Bounded Fallback in Kiwi Diagnoses (`_settle_unresolved` -> `_withheld`)**:
   If a Kiwi diagnosis receives a false flag on a legitimate diagnostic sentence (e.g., describing
   a blocking session holding row locks), the model is asked to revise. If the revision repeats the
   observation or cannot be reconciled, `_settle_unresolved` attempts excision.
   If excision leaves an empty text, cannot locate the statement, or the excised text still triggers
   a finding, `_settle_unresolved` returns `None`.
   When `settled is None`, `_KiwiRun` invokes `_withheld()`, discarding the model's entire response
   and replacing it with `render_fallback()`. Bounded fallback outputs a generic lookup listing with
   "Unknown" root cause and no proposed remediation, causing hard failure on all DIAG-* and KINJ-* rubrics.

## 4. Requester Rendering Assessment (`next_checks._render_step`)

In `next_checks._render_step`, the rendering logic was adjusted:
```python
# Requester access is unverified metadata: silently omit it, keeping the question.
# Only actors whose role bears access may publish an access description.
if step.actor in ("account_with_access", "dba") and step.access:
    actor += f" ({step.access.strip()})"
```

- **Architectural Correctness**:
  - `requester` steps represent queries for external user knowledge (e.g., application configuration
    or deployment targets outside the database). Requesters do not hold database privileges.
  - Declining the step would penalize legitimate, necessary user-facing questions.
  - Silently omitting `access` while rendering the question (`For you to supply, outside these lookups: <question>`)
    correctly prevents unverified free-text model assertions (such as `only the person running the job knows...`)
    from being rendered under harness attribution.
  - Phrase safety (`_safe_phrase`) is still enforced during `validate()`, ensuring malicious or
    multiline markdown text in `access` still declines the step.
- **Model Free Text Leakage**:
  - In harness-rendered sections (`rendered: next_checks`), only `step.about` (prefixed as an open question)
    and `step.access` for `account_with_access` and `dba` (guarded by `_safe_phrase`) are rendered.
  - All model next-steps prose outside the JSON block is cleanly stripped by `replace_section`.
  - In settlement sections (`rendered: claim_settlement`), only harness-authored explanation text
    and finding definitions are appended. No unvalidated model free text leaks into harness-authored sections.

## Recommendations

1. **Refine `_LOCK_WAIT` to Require Wait Context for `blocking` and `row locks`**:
   Bare `blocking` should only match when functioning as the subject/object of an exception
   verb (e.g. `\b(?:bare blocking|blocking itself)\b`), or require trailing `waits?|conflicts?`.
   Noun phrases like `blocking session`, `blocking chain`, `blocking lock`, and `blocking transaction`
   should be explicitly excluded from `_LOCK_WAIT`.
2. **Expand `_WAIT_DENIAL` to Include Prepositional Negations**:
   Add `without\s+(?:raising|throwing|causing|signaling|generating)` and `free\s+of\s+errors?`
   to `_WAIT_DENIAL` so legitimate explanations of non-raising concurrency mechanisms do not trigger false flags.
3. **Add `mask\w*` to `_EXCEPTION_ACTION`**:
   Include `mask\w*` in `_EXCEPTION_ACTION` and `_EXCEPTION_CONTEXT` to catch active phrasing like
   `"The handler masks lock waits"`.
4. **Add Subclause Split on Unpunctuated Subordinating Conjunctions**:
   In `subclauses()`, split on `\s+while\s+` and `\s+whereas\s+` even when unpunctuated by a preceding comma,
   preventing independent diagnostic clauses from bleeding into each other.
