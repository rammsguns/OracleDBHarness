### 1.1 Oracle Database 19c Accuracy Assessment

The prompt updates in `context.py` and finding descriptions in `claim_checks.py` and `edit_contract.py` were audited against Oracle Database 19c specifications:

1. **`RAISE_APPLICATION_ERROR` numeric range (-20000..-20999) & ORA-21000**:
   - In Oracle PL/SQL, `RAISE_APPLICATION_ERROR` takes an integer in the range `-20000` to `-20999`. Passing any number outside this range (such as positive `20001`, `0`, `-19999`, or `-21000`) causes Oracle to raise runtime exception:
     `ORA-21000: error number argument to raise_application_error of <val> is out of range`.
   - The prompt text (`using a number in -20999..-20000`) and the check logic in `claim_checks.py` (`-20999 <= value <= -20000`) are strictly accurate.
2. **`ROW_NUMBER` top-N cardinality**:
   - `ROW_NUMBER() OVER (...)` assigns sequential integers starting at 1 within each partition. A top-N query (`WHERE rn <= N`) returns *at most N* rows per partition; when fewer rows exist in a group, fewer rows are returned.
   - The prompt rule (`A top-N per group using ROW_NUMBER returns at most N rows per group, fewer when fewer qualify; do not say exactly N`) is strictly accurate and prevents ungrounded claims of exact row counts.
3. **Unique-Key lookup preservation**:
   - The prompt explicitly preserves unique lookup as the primary valid approach: `"Look the row up by a unique key, or handle TOO_MANY_ROWS explicitly..."`
   - It does not force exception handling when a unique predicate exists.
4. **"Names the ambiguous key" wording**:
   - The prompt instructs: `handle TOO_MANY_ROWS explicitly by raising a named application error with RAISE_APPLICATION_ERROR using a number in -20999..-20000 that names the ambiguous key. Returning NULL or another sentinel hides the ambiguity.`
   - In PL/SQL design, embedding the offending key in the error message (e.g., `'Ambiguous salary lookup for last_name ' || p_last_name`) provides actionable diagnostics and prevents ambiguous returns.

## 3. Fallback and Repair Risk Analysis

The anchor-repair path in `services/api/harness_api/copilot/service.py` was inspected to determine whether a false ambiguity-handler flag on a proposal could cause:
1. **A failed repair**:
   - If a proposal falsely triggers `ambiguity_handler_problems`, `service.py:804` appends the finding to `anchors`.
   - The harness skips immediate delivery (`repair: "none"`) and issues an anchor repair request to the LLM (`service.py:820`).
   - If the LLM's repair reply times out, returns malformed Markdown, or repeats the perceived pattern, the repair outcome settles as `repair: "failed:anchor"` (or `failed:missing` / `failed:wall_time`).
2. **A withheld proposal**:
   - In `service.py:841-853`, when an anchor repair fails, control exits `_check_edit_contract` without overwriting `plain.reading`.
   - In `service.py:697`, `_capture_proposal` receives the original accepted reading (`plain.reading`), and `yield ("proposal", proposal)` emits the first proposal.
   - **Conclusion**: The proposal is **not withheld**; the first proposal stands. However, its metadata records `repair: "failed:anchor"`.
3. **A narrow-rubric failure**:
   - If an evaluation rubric requires clean proposals without repairs (or checks `contract["repair"] in ("none", "repaired")`), recording `failed:anchor` causes a test/rubric failure.
   - Furthermore, because `anchor_repair_message` commands the model to rewrite its code, the model may attempt an unnecessary restructuring that introduces real syntax errors or functional bugs, jeopardizing subsequent compile or D1 gates.
